# 路上改标准流程（L4 旅途中修改时读取）

旅途中用户在赶路，每步都要快、都不能错。按顺序执行：

1. **解析消息**：哪天 / 什么动作（加途经点、改路线、删 POI）/ 哪个地方。
2. **新地名走三步验证**（路上改最常在这一步翻车）：
   - 路名、路口、驿站、观景台这类非行政地名，**禁止裸用 `maps_geo`**——它返回所在城市质心。实测案例："乌苏驿"被落到乌苏市中心，偏 10km，用户在路上等着，来回修了六轮；
   - 正确流程：`maps_text_search` 找候选 → 核对详情确认是目标 POI → 用该坐标跑一次 `maps_direction_driving` 验证路耗量级合理。
3. **途经点方向核对**：新途经点应大致落在该段起终点之间。加"高速入口"这类点时尤其要查——实测案例：往东走的段（恰甫其海 82.49°E → 蜜蜂小镇 83.43°E）被加了西边的高速出口（82.23°E），等于反方向绕路。
4. **只重算受影响段**：改 D6 就只重取 D6 相关 segments 的路耗和几何，不整天重算，更不全程重算——这是 token 和 API 配额双省的关键。
5. **删 POI 全链清理**：stops 里的对象、受影响 segments 的合并、当日 km/h 重算、claims 里的引用，一个都不能漏。
6. **重跑校验 → 重渲染 → 回复带数字**：确认话术里必须给出新段的 km/h 变化，让用户看到改动的代价。
7. **顺带滚动复检**：把未来 48 小时内将途经的 seasonal_road / reservation 类 claim 快速重查一遍——这两类规则可能昨天刚上线（实例：某公路预约制在旅行季中途生效，公告到执行只有 6 天，早两周走的人全程无感）。查到新规先看 `effective_from` 与剩余行程的关系（已生效/未生效/行程中途生效，第三种高亮告知）。
